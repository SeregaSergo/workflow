- итерация по связанным задачам

- запросы документов
- определить области задачи, которые требуют уточнения после исследования

###### Артефакты:

- task_qa_1.md (optional)

### Review
###### Входные данные
- данные задачи
- номер итерации
###### Задачи:
- Исследовать задачу
- Найти diff между коммитом от которого создавалась ветка и текущим
- Выполнить ревью кода по пунктам
- Сформировать задачи на доработку, если есть критичные замечания
###### Результат:
- Отчет о полноте и корректонсти выполнения задачи
- Задача на исправление
###### Инструменты:
- скрипт получения diff'a
###### Артефакты:
- reveiw_{iteration}.md
- task_{iteration}.md (optional)
###### Поведение:
- Если есть критичные замечания (блок `<feedback>` в ответе LLM) — статус `ok`,
  переход в `plan` с увеличением `iteration` (через `RepeatAt("plan")` в
  transition `review_next`).
- Если замечаний нет — статус `ok`, переход в `mr`. Чтобы дать пользователю
  ручную проверку diff'a перед созданием MR, добавь `mr` в
  `workflows.<workflow>.pause_before` в конфиге — движок остановится перед
  фазой `mr` и попросит `wf resume`. См. раздел [Конфигурируемая
  остановка](#конфигурируемая-остановка-pause_before).

### Конфигурируемая остановка (`pause_before`)

Поле `workflows.<workflow>.pause_before: list[str]` в конфиге задаёт фазы,
**перед** которыми движок останавливается с exit code 3 и просит `wf resume`.
Артефакты остановленной фазы ещё не созданы — пользователь смотрит на результат
предыдущей фазы.

- Дефолт — пустой список: без пауз.
- Имена в списке должны соответствовать фазам workflow; иначе CLI сразу падает с
  понятной ошибкой.
- Пауза для фазы N эмитится не больше одного раза за один заход в фазу:
  `state.pause_consumed_for` фиксирует "пауза израсходована", `wf resume`
  возвращается в ту же фазу, пауза пропускается, фаза запускается.
- После любого перехода (`review → plan` через `RepeatAt`, `plan → implement` и
  т.д.) `pause_consumed_for` сбрасывается, поэтому в цикле `review → plan → … →
  mr` пауза перед `mr` сработает на каждой итерации.

### MR
###### Входные данные
- `state.worktree`, `state.branch`, `state.base_branch`, `state.task_id`,
  `state.task_url`
- `state.mr_url` (используется для идемпотентности — если уже задан,
  инструмент не вызывается повторно)
###### Задачи:
- Вызвать внешний инструмент `create_mr` (cwd = worktree)
- Прочитать URL мерж-реквеста из последней непустой строки stdout
- Сохранить URL в `state.mr_url`
###### Результат:
- Мерж реквест создан
- `state.mr_url` заполнен (используется фазой `notify`)
- Событие `external_tool` в `events.jsonl` со stdout / stderr / exit code (см. `summary.md`)
###### Инструменты:
- `tools.create_mr` (см. [default-config.yaml](../src/wf/default-config.yaml)):
  - cwd = `state.worktree`
  - jinja2-контекст: `branch`, `base_branch`, `task_id`, `task_url`, `worktree`
  - контракт: команда должна писать URL в stdout (последняя непустая строка
    — `http://…` или `https://…`); ненулевой exit или отсутствие URL —
    `PhaseResult.failed`
###### Поведение:
- Если `state.mr_url` уже задан — фаза сразу возвращает `ok` (идемпотентность).
- Если `tools.create_mr` не сконфигурирован — `is_ready() == False`, движок
  останавливается с ошибкой о неготовности фазы.

### Notify
###### Входные данные
- `state.mr_url` (заполняется фазой `mr` — без него `is_ready()` вернёт `False`)
- `state.task_id`, `state.task_url`, `state.task_title`
- `workflows.<workflow>.notify_channel_id` и `workflows.<workflow>.reviewers`
  из конфига (если `task_title` пуст — в сообщение подставляется `task_id`;
  из пула `reviewers` случайно выбираются 2 имени через `random.sample`,
  если пул короче — берётся всё, что есть; если пуст — строка "ревью " без значения)
###### Задачи:
- Отрендерить сообщение по шаблону
  [notify_message.txt.j2](../src/wf/templates/notify_message.txt.j2)
- Вызвать внешний инструмент `notify` с позиционными аргументами
  `<channel_id> <message>`
###### Результат:
- Нотификация отправлена
- Событие `external_tool` в `events.jsonl` со stdout / stderr / exit code (см. `summary.md`)
###### Инструменты:
- `tools.notify` (см. [default-config.yaml](../src/wf/default-config.yaml)):
  - cwd = `state.worktree`
  - jinja2-контекст: `channel_id`, `message`
  - контракт: ненулевой exit — `PhaseResult.failed` (stderr попадает в reason),
    stdout не парсится
###### Поведение:
- `is_ready() == False`, если `tools.notify` не сконфигурирован, `state.mr_url`
  пуст или `workflows.<workflow>.notify_channel_id` не задан — движок
  останавливается с ошибкой о неготовности фазы.
- На ненулевой exit фаза возвращает `failed`; `wf resume` повторяет вызов
  (фаза `mr` повторно не выполняется благодаря идемпотентности по `state.mr_url`).

### Cleanup worktree
###### Входные данные
- `state.worktree`, `state.repo_path`
###### Задачи:
- Удалить git worktree, созданный на фазе `prepare`, через
  `wfgit.remove_worktree(repo_path, worktree)` (идемпотентно: `git worktree
  remove --force` + `shutil.rmtree` + `git worktree prune`, все с `check=False`).
- На успехе обнулить `state.worktree`, чтобы `wf status` не показывал
  висячий путь. Engine сохранит state после фазы.
- Артефакты задачи (`state.json`, `events.jsonl`, `summary.md`, `artifacts/`)
  не трогаются — для post-mortem.
###### Результат:
- Worktree удалён с диска
- `state.worktree = None`
- Событие `phase_note` в `events.jsonl` с описанием результата
###### Поведение:
- `is_ready() == True` всегда — все edge cases обрабатываются внутри `run()`.
- Если `state.worktree is None` (например, `prepare` не выполнялся, или фаза
  запускается повторно после `wf resume`) — `phase_note "skipped"`, `ok`.
- Если после `remove_worktree` директория всё ещё существует (занятые файлы,
  нет прав и т.д.) — yellow warn в console + `phase_note "WARN: …"`, но всё
  равно возвращает `ok`. Причина: к моменту этой фазы MR создан и
  уведомление отправлено — валить задачу в `terminal=failed` из-за cleanup
  было бы дезориентирующим. Остаток можно дочистить через `wf remove`.
